    6. Capítulo 5 - O cliente [Angular] da aplicação [RdvMedecins]

    Este capítulo detalha, arquivo por arquivo, o conteúdo da pasta [rdvmedecins-angular-client] incluída neste documento, usando o formato adotado ao longo deste curso: código-fonte numerado linha a linha, seguido de uma seção intitulada “Vamos comentar este código:”. Cada pasta de projeto também contém seu próprio arquivo README.md.

    6.1. Visão geral da arquitetura

    Como no documento original, o cliente segue uma arquitetura em camadas, que chamaremos aqui de V-C-Services (View-Controller-Services):

    Vale destacar uma diferença de terminologia: no AngularJS 1.x, a View (o template HTML) e o Controller (a classe JavaScript associada) eram duas entidades distintas, ligadas por $scope. No [Angular], elas são reunidas em uma única entidade, o componente (veja o capítulo anterior) — e é por isso que, daqui em diante, falaremos simplesmente em “componentes” onde o documento original distinguia entre view e controller.

    Como no documento original, os componentes NUNCA se comunicam diretamente com o servidor: esse papel é reservado exclusivamente à camada de serviços. Trata-se de um princípio de projeto que se aplica igualmente ao AngularJS 1.x e ao [Angular] — não mudou.

    6.2. Árvore do projeto

    Esta estrutura segue diretamente o fluxo do documento original (login, seleção de médico/dia, exibição da agenda, marcação de consulta), organizada aqui simplesmente em componentes [Angular] standalone, em vez de controllers e views separados do AngularJS 1.x.

    O Bootstrap é usado em todas as views ([node_modules/bootstrap/dist/css/bootstrap.min.css], declarado em angular.json) — uma evolução direta do Bootstrap 3, que já era usado pelo documento original.

      import { inject } from '@angular/core';
  import { HttpErrorResponse, HttpInterceptorFn } from '@angular/common/http';
  import { catchError, throwError } from 'rxjs';
  import { AuthService } from '../services/auth.service';

  export const authInterceptor: HttpInterceptorFn = (request, next) => {
    const auth = inject(AuthService);
    const token = auth.accessToken();

   const requestWithToken = token
     ? request.clone({ setHeaders: { Authorization: `Bearer ${token}` } })
     : request;

   return next(requestWithToken).pipe(
     catchError((error: unknown) => {
       if (error instanceof HttpErrorResponse && error.status === 401) {
         auth.logOut();
       }
       return throwError(() => error);
     }),
   );
 };

    Vamos comentar este código:

    • Linha 6: [export const authInterceptor: HttpInterceptorFn = (request, next) => {] — Há algumas versões, o [Angular] privilegia os interceptors funcionais ([HttpInterceptorFn]) — uma simples função — em vez dos interceptors baseados em classes das versões anteriores do [Angular]: mais curtos de escrever e mais simples de registrar (veja app.config.ts, withInterceptors([...]));
    • linhas 10–12: [request.clone({ setHeaders: { Authorization: `Bearer ${token}` } }) : request;] — uma requisição do [HttpClient] é um objeto imutável — não é possível modificar seus cabeçalhos diretamente; é preciso criar uma cópia modificada. É essa cópia (requestWithToken) que deve ser repassada pela cadeia, nunca a requisição original, não modificada;
    • linhas 15–18: [catchError((error) => { if (error instanceof HttpErrorResponse && error.status === 401) { auth.logOut(); } … })] — um erro 401 durante uma sessão significa que o token não é mais válido (expirou, ou o servidor foi reiniciado): o cliente é desconectado de forma adequada, em vez de ser deixado em um estado inconsistente (aparentemente conectado, mas sem que nenhuma requisição tenha êxito);
    • linha 19: [return throwError(() => error);] — o erro é relançado como está após esse tratamento: o interceptor não deve ocultar o erro do código chamador ([ScheduleComponent] via [App], por exemplo), mas apenas tratar um caso específico de passagem.

    Poderíamos adicionar manualmente Authorization: Bearer ... a cada um dos métodos de AppointmentService. Um interceptor evita essa repetição: a pergunta “Como autenticamos uma requisição?” é respondida em um único lugar, de uma vez por todas, e passará a valer automaticamente para qualquer serviço futuro que use HttpClient. Ele é registrado em app.config.ts (abaixo), por meio de provideHttpClient(withInterceptors([authInterceptor])): sem essa linha, a função existiria, mas nunca seria chamada.

    Por que não usar o JavaScript do Bootstrap? Porque o Bootstrap e o [Angular] passariam a gerenciar, cada um por conta própria, a mesma informação (o modal está aberto?) — uma fonte clássica de bugs sutis em uma aplicação Angular. Ao deixar open() (um signal e, portanto, o estado [Angular]) controlar sozinho a exibição, temos uma única fonte de verdade, mantendo exatamente a aparência visual de um modal do Bootstrap. O documento original (2014) usava um componente da biblioteca angular-ui-bootstrap (um modal “pronto para uso” do AngularJS 1.x), já concebido segundo esse mesmo princípio: estado gerenciado pelo [Angular], aparência emprestada do Bootstrap.

    6.11. O componente raiz [App]: orquestrador e guardião da autenticação

Desde a adição da autenticação, ele assumiu um segundo papel: o de “porteiro” da camada de apresentação, que decide se exibe a tela de login ou o restante da aplicação.

  import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
  import { TranslatePipe } from '@ngx-translate/core';
  import { AppointmentService } from './core/services/appointment.service';
  import { SettingsService } from './core/services/settings.service';
  import { AuthService } from './core/services/auth.service';
  import { LanguageService } from './core/services/language.service';

 @Component({
   selector: 'app-root',
   imports: [DoctorDayPickerComponent, ScheduleComponent, BookingDialogComponent, LoginComponent, TranslatePipe],
   templateUrl: './app.html',
   styleUrl: './app.css',
 })
 export class App {
   private readonly appointmentService = inject(AppointmentService);
   private readonly destroyRef = inject(DestroyRef);
   protected readonly settings = inject(SettingsService);
   protected readonly auth = inject(AuthService);
   protected readonly language = inject(LanguageService);

   protected readonly doctors = signal<Doctor[]>([]);
   protected readonly clients = signal<Client[]>([]);
   protected readonly schedule = signal<DoctorDaySchedule | null>(null);
   protected readonly error = signal<string | null>(null);
   protected readonly slotBeingBooked = signal<SlotJson | null>(null);

   private lastDoctorId: number | null = null;
   private lastDay: string | null = null;

   constructor() {
     effect(() => {
       if (this.auth.isLoggedIn()) {
         this.loadInitialLists();
       }
     });
   }

   private loadInitialLists(): void {
     this.appointmentService.getAllDoctors().pipe(takeUntilDestroyed(this.destroyRef)).subscribe({
       next: (doctors) => this.doctors.set(doctors),
       error: (err) => this.error.set(String(err.message ?? err)),
     });
     this.appointmentService.getAllClients().pipe(takeUntilDestroyed(this.destroyRef)).subscribe({
       next: (clients) => this.clients.set(clients),
       error: (err) => this.error.set(String(err.message ?? err)),
     });
   }

   onLogout(): void {
     this.auth.logOut();
     this.doctors.set([]);
     this.clients.set([]);
     this.schedule.set(null);
     this.error.set(null);
     this.slotBeingBooked.set(null);
     this.lastDoctorId = null;
     this.lastDay = null;
   }

   onSearchSchedule(criteria: { doctorId: number; day: string }): void {
     this.error.set(null);
     this.lastDoctorId = criteria.doctorId;
     this.lastDay = criteria.day;
     this.loadSchedule();
   }

   onBookingRequest(slot: SlotJson): void {
     this.slotBeingBooked.set(slot);
   }

   onConfirmBooking(choice: { clientId: number }): void {
     const slot = this.slotBeingBooked();
     if (slot === null || this.lastDay === null) {
       return;
     }
     this.appointmentService.addAppointment(this.lastDay, choice.clientId, slot.id)
       .pipe(takeUntilDestroyed(this.destroyRef))
       .subscribe({
         next: () => { this.slotBeingBooked.set(null); this.loadSchedule(); },
         error: (err) => this.error.set(String(err.message ?? err)),
       });
   }

   onCloseBooking(): void {
     this.slotBeingBooked.set(null);
   }

   onCancelAppointment(appointment: AppointmentJson): void {
     this.appointmentService.deleteAppointment(appointment.id).pipe(takeUntilDestroyed(this.destroyRef)).subscribe({
       next: () => this.loadSchedule(),
       error: (err) => this.error.set(String(err.message ?? err)),
     });
   }

   private loadSchedule(): void {
     if (this.lastDoctorId === null || this.lastDay === null) {
       return;
     }
     this.appointmentService.getDoctorScheduleOfDay(this.lastDoctorId, this.lastDay)
       .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe({
        next: (schedule) => this.schedule.set(schedule),
        error: (err) => this.error.set(String(err.message ?? err)),
      });
  }
 }

    Vamos comentar este código:

    • linha 12: [imports: [DoctorDayPickerComponent, ScheduleComponent, BookingDialogComponent, LoginComponent, TranslatePipe],] — um componente standalone declara os componentes e pipes que usa em seu template — [LoginComponent] foi adicionado a esta lista por causa da autenticação, e [TranslatePipe] por causa da tradução;
    • linha 20: [protected readonly auth = inject(AuthService);] — exposto ao template (protected, não private) para o badge de papel/nome e o botão de logout (veja [app.html]);
    • linha 21: [protected readonly language = inject(LanguageService);] — exposto ao template para os dois botões FR/EN na barra de navegação, que estão sempre visíveis (inclusive na tela de login), ao contrário do restante da interface;
    • Linha 33: [effect(() => { if (this.auth.isLoggedIn()) { this.loadInitialLists(); } });] — `effect()` executa novamente seu corpo toda vez que um signal que ele monitora muda — neste caso, isLoggedIn(). Ele também é executado uma vez imediatamente: se uma sessão já estava armazenada em localStorage (recarga da página), as listas são carregadas logo na inicialização, sem esperar um novo login;
    • linha 40: [private loadInitialLists(): void {] — quando um usuário passa a estar autenticado (login bem-sucedido ou sessão restaurada), as listas de médicos e clientes são carregadas de uma vez por todas — o equivalente, no lado do cliente, do que [ApplicationModelService] fazia quando o servidor era iniciado (Capítulo 3). Como todos os endpoints do servidor agora são protegidos por [JwtAuthGuard], seria inútil de qualquer forma (e causaria erros 401) fazer essa chamada antes do login;
    • linha 51: [onLogout(): void {] — responde ao botão “Log out”: limpa a sessão e todo o estado de negócio exibido (linhas 53–59) — sem isso, um novo usuário que fizesse login em seguida veria brevemente a agenda do usuário anterior;
    • Linhas 41, 45, etc.: [.pipe(takeUntilDestroyed(this.destroyRef))] — uma assinatura RxJS (.subscribe(...)) permanece ativa até ser explicitamente cancelada; este é um descuido comum e uma fonte de vazamentos de memória. Este operador cancela a assinatura automaticamente assim que o componente é destruído;
    • linha 69: [onBookingRequest(slot: SlotJson): void { this.slotBeingBooked.set(slot); }] — ainda não chama o servidor: apenas abre a janela de reserva. É onConfirmBooking (linha 73), acionado pelo evento (confirm) de [BookingDialogComponent], que de fato chama addAppointment;
    • Linhas 81, 92: [this.loadSchedule();] — após uma reserva ou cancelamento bem-sucedido, loadSchedule() é chamado novamente: isso permite que a agenda exibida reflita imediatamente o novo status, sem que o usuário precise atualizar a página.
