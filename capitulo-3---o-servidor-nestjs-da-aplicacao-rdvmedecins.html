-- Este script reproduz EXATAMENTE o esquema relacional do documento original
-- (2014, Spring 4 / Spring Data / MySQL 5): mesmas tabelas, mesmas colunas,

-- para-muitos - uma simplificação didática deliberada, documentada

-- partimos de um banco de dados vazio a cada execução do script (prático em desenvolvimento)

 DROP TABLE IF EXISTS slots;
 DROP TABLE IF EXISTS clients;
 DROP TABLE IF EXISTS doctors;
 DROP TABLE IF EXISTS users;

 CREATE DATABASE IF NOT EXISTS dbrdvmedecins CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
 USE dbrdvmedecins;

 CREATE TABLE doctors (
   id         INT AUTO_INCREMENT PRIMARY KEY,
   version    INT NOT NULL DEFAULT 0,
   title      VARCHAR(5)  NOT NULL,
   last_name  VARCHAR(20) NOT NULL,
   first_name VARCHAR(20) NOT NULL
 );

 CREATE TABLE clients (
   id         INT AUTO_INCREMENT PRIMARY KEY,
   version    INT NOT NULL DEFAULT 0,
   title      VARCHAR(5)  NOT NULL,
   last_name  VARCHAR(20) NOT NULL,
   first_name VARCHAR(20) NOT NULL
 );

 CREATE TABLE slots (
   id           INT AUTO_INCREMENT PRIMARY KEY,
   version      INT NOT NULL DEFAULT 0,
   doctor_id    INT NOT NULL,
   start_hour   INT NOT NULL,
   start_minute INT NOT NULL,
   end_hour     INT NOT NULL,
   end_minute   INT NOT NULL,
   CONSTRAINT fk_slots_doctor FOREIGN KEY (doctor_id) REFERENCES doctors(id)
 );

 CREATE TABLE appointments (
   id         INT AUTO_INCREMENT PRIMARY KEY,
   version    INT NOT NULL DEFAULT 0,
   day        DATE NOT NULL,
   slot_id    INT NOT NULL,
   client_id  INT NOT NULL,
   CONSTRAINT fk_appointments_slot   FOREIGN KEY (slot_id)   REFERENCES slots(id),
   CONSTRAINT fk_appointments_client FOREIGN KEY (client_id) REFERENCES clients(id),
   CONSTRAINT unq1_appointments UNIQUE (day, slot_id)
 );

 CREATE TABLE users (
   id       INT AUTO_INCREMENT PRIMARY KEY,
   version  INT NOT NULL DEFAULT 0,
   login    VARCHAR(30) NOT NULL UNIQUE,
   password VARCHAR(100) NOT NULL,
   name     VARCHAR(40) NOT NULL,
   role     VARCHAR(10) NOT NULL
 );

    Comentando este código:

    • linhas 20–24: [DROP TABLE IF EXISTS …] : o script parte de um banco vazio a cada execução, na ordem inversa das dependências (começando por `appointments`, que referencia `[slots]` e `clients`, até `users`, que ninguém referencia): o [MySQL] se recusaria a excluir uma tabela ainda referenciada por uma chave estrangeira;
    • linha 48: [doctor_id INT NOT NULL], depois linha 53: [CONSTRAINT fk_slots_doctor FOREIGN KEY …] : um horário sempre pertence a um médico;
    • linha 64: [CONSTRAINT unq1_appointments UNIQUE (day, slot_id)] : a regra de negócio central da aplicação: o mesmo horário no mesmo dia só pode ser reservado uma vez. É essa restrição, e somente ela, que impede uma consulta duplicada; nem o validador nem a camada de negócio a reverificam explicitamente (veja abaixo, addAppointment);
    • linhas 67–74: [CREATE TABLE users (…)] : a tabela adicionada nesta etapa. `login` é UNIQUE (dois usuários não podem ter o mesmo login); `password` armazena uma senha com hash bcrypt (nunca em texto puro); role é 'ADMIN' ou 'USER', uma simples coluna de texto, ao passo que o documento original usava três tabelas (users, roles, users_roles) para permitir vários papéis por usuário. Como esta aplicação exige apenas dois papéis mutuamente exclusivos, a relação muitos-para-muitos original seria exagerada;
    • linhas 91–93: [INSERT INTO users …] : duas contas de demonstração, admin/admin (papel ADMIN) e user/user (papel USER), com as senhas já com hash bcrypt (10 rounds de salt), nunca em texto puro, nem mesmo neste script de demonstração.

    4.3. As entidades [TypeORM] (src/entities/)

    As entidades são as classes que representam linhas de tabelas do banco de dados como objetos TypeScript, o equivalente direto das entidades JPA do projeto original (pacote rdvmedecins.entities).

      import { [PrimaryGeneratedColumn], [VersionColumn] } from 'typeorm';

  export abstract class AbstractEntity {
    @PrimaryGeneratedColumn()
    id: number;

    @VersionColumn()
    version: number;
  }

    Comentando este código:

    • linha 4: [@PrimaryGeneratedColumn()] : declara uma chave primária autoincrementada pelo SGBD, o equivalente exato de @Id + @GeneratedValue(strategy = GenerationType.AUTO) no JPA;
    • linha 7: [@VersionColumn()] : o mecanismo nativo do [TypeORM] para bloqueio otimista: o [TypeORM] incrementa automaticamente essa coluna a cada modificação e gera um erro se você tentar salvar uma entidade cuja versão não corresponde mais à do banco de dados (alguém a modificou nesse meio tempo); o equivalente exato de @Version no JPA/Hibernate;
    • linha 3: [export abstract class AbstractEntity {] : essa classe não é decorada por [@Entity]: ela não corresponde a nenhuma tabela por si só. O [TypeORM] chama essa técnica de “Concrete Table Inheritance”: cada subclasse decorada por [@Entity] recebe sua própria tabela, com todas as colunas herdadas; o equivalente exato de @MappedSuperclass no JPA.

      import { [Column], [Entity], [JoinColumn], [ManyToOne], [RelationId] } from 'typeorm';
  import { AbstractEntity } from './abstract.entity';
  import { Doctor } from './doctor.entity';

  @Entity({ name: 'slots' })
  export class Slot extends AbstractEntity {
    @Column({ name: 'start_hour' }) startHour: number;
    @Column({ name: 'start_minute' }) startMinute: number;
    @Column({ name: 'end_hour' }) endHour: number;
   @Column({ name: 'end_minute' }) endMinute: number;

   @ManyToOne(() => Doctor, (doctor) => doctor.slots)
   @JoinColumn({ name: 'doctor_id' })
   doctor: Doctor;

   @RelationId((slot: Slot) => slot.doctor)
   doctorId: number;
 }

    Comentando este código:

    • linhas 7–10: [@Column({ name: 'start_hour' }) startHour: number; …] — os quatro limites de tempo do horário de consulta (hora/minuto de início e de fim), quatro inteiros simples, cada um mapeado explicitamente para sua coluna snake_case (start_hour, start_minute, end_hour, end_minute);
    • linha 12: [@ManyToOne(() => Doctor, (doctor) => doctor.slots)] : vários horários pertencem ao mesmo médico. Por padrão, o [TypeORM] não carrega a relação “doctor” ao ler um horário (comportamento “lazy” padrão): é preciso solicitá-la explicitamente (opção relations: [...] em uma consulta); exatamente como FetchType.LAZY exigia, no lado JPA, um `left join fetch` explícito na consulta JPQL para recuperar o médico;
    • linha 13: [@JoinColumn({ name: 'doctor_id' })] : especifica o nome da coluna de chave estrangeira na tabela [slots];
    • linha 16: [@RelationId((slot: Slot) => slot.doctor)] : o equivalente exato e idiomático, no lado do [TypeORM], do campo somente leitura idMedecin do projeto original ([@Column](name = "id_medecin", insertable = false, updatable = false)): ele expõe diretamente o valor da chave estrangeira, sem precisar carregar toda a entidade [Doctor]; útil para construir respostas JSON leves (veja abaixo, a camada web).

    Nota: um campo [@RelationId] é uma coluna virtual, calculada posteriormente pelo [TypeORM]; não é uma verdadeira coluna SQL utilizável em uma cláusula WHERE de um “query builder” (veja abaixo, [SlotRepository]). Serve apenas para recuperar o valor da chave estrangeira depois que a entidade foi carregada.

  import { AbstractEntity } from './abstract.entity';
  import { Client } from './client.entity';
  import { Slot } from './slot.entity';

  @Entity({ name: 'appointments' })
  @Unique('unq1_appointments', ['day', 'slot'])
  export class Appointment extends AbstractEntity {
    @Column({ type: 'date' })
   day: string;

   @ManyToOne(() => Client)
   @JoinColumn({ name: 'client_id' })
   client: Client;

   @ManyToOne(() => Slot)
   @JoinColumn({ name: 'slot_id' })
   slot: Slot;

   @RelationId((appointment: Appointment) => appointment.client)
   clientId: number;

   @RelationId((appointment: Appointment) => appointment.slot)
   slotId: number;
 }

    Comentando este código:

    • linha 7: [@Unique('unq1_appointments', ['day', 'slot'])] : referencia, no lado do [TypeORM], a restrição SQL do script do banco de dados. Atenção: aqui referenciamos o nome da relação (“slot”), e não o campo [@RelationId] (“slotId”); este último é uma coluna virtual, que o [TypeORM] não aceita em uma restrição @Unique. O próprio [TypeORM] mapeia 'slot' para sua coluna real de chave estrangeira (slot_id);
    • linha 9: [@Column({ type: 'date' })] : tipo 'date' (e não 'datetime'): só o dia é mantido, não a hora; exatamente como TemporalType.DATE especificava no lado JPA;
    • linhas 12–18: [@ManyToOne(...) / @JoinColumn(...)] : duas relações, com [Client] e com [Slot], seguindo o mesmo princípio de [slot.entity.ts];
    • linhas 20–24: [@RelationId(...)] : os equivalentes somente leitura dos campos idClient/idCreneau do projeto original (mesmo mecanismo de Slot.doctorId, veja acima).

    4.5. A camada DAO (src/repositories/)

    A camada DAO (Data Access Object) é a única parte do projeto que se comunica diretamente com o TypeORM/MySQL; o equivalente das interfaces Spring Data do projeto original (pacote rdvmedecins.repositories).

    A diferença mais importante a entender entre o Spring Data e o [TypeORM]: com o Spring Data, bastava declarar uma interface (extends CrudRepository<...>) para obter automaticamente os métodos básicos (findAll, findOne, save, delete…); o próprio Spring gerava, na inicialização, uma classe que a implementava. Com o [TypeORM], não há geração automática de uma implementação a partir de uma interface: injetamos diretamente o Repository<Entity> genérico fornecido pelo [TypeORM] (via [@InjectRepository]) e escrevemos nós mesmos os métodos que queremos expor, apoiando-nos nos métodos predefinidos desse Repository ou usando o query builder para consultas mais específicas.

    4.8. Autenticação (src/auth/)

    Esta seção documenta a adição, nesta etapa do curso, da autenticação por token (JWT) e do controle de acesso baseado em papéis (ADMIN/USER); o equivalente funcional da camada Spring Security do documento original, reescrita com ferramentas padrão do ecossistema [NestJS]: [@nestjs/passport] e @nestjs/jwt.

    Duas diferenças intencionais em relação ao projeto original, documentadas aqui de uma vez por todas:

    1. JWT em vez de HTTP Basic. O projeto Spring original enviava o cabeçalho Authorization: Basic <login:senha em Base64> em toda requisição: a senha (codificada, não criptografada) era, portanto, transmitida pela rede a cada chamada. Este port usa um token no lugar: JWT (JSON Web Token). A senha é apresentada uma única vez, no login (POST /login); o servidor devolve então um token assinado, que o cliente inclui em todas as requisições seguintes (cabeçalho Authorization: Bearer <token>). Essa é a prática atual para esse tipo de API, como já mencionado na conclusão do capítulo anterior.
    2. Um único papel por usuário, em uma única coluna do banco de dados, em vez do relacionamento muitos-para-muitos (users/roles/users_roles) do projeto original — veja user.entity.ts acima.

    Um ponto de arquitetura a entender antes de ler o código a seguir: quando um guard rejeita uma requisição (401 Unauthorized, 403 Forbidden), a resposta nunca passa pelo envelope habitual [ServerResponse]<T> ({ status, data }): o [NestJS] responde diretamente em seu formato JSON nativo, { statusCode, message, error }. Trata-se de uma escolha deliberada: os erros de segurança são tratados antes de entrar no controller (por um guard), enquanto [ServerResponse]<T> é gerado pelo controller para os erros de negócio (recurso não encontrado, data inválida etc.). O cliente [Angular] deve, portanto, distinguir esses dois tipos de resposta de erro (veja o próximo capítulo, auth.interceptor.ts).

       context.getHandler(),
       context.getClass(),

   constructor(

     private readonly jwtService: JwtService,
   ) {}

   async validateUser(login: string, password: string): Promise<User | null> {
     const user = await this.userRepository.findByLogin(login);
     if (user === null) {
       return null;
     }
     const passwordCorrect = await bcrypt.compare(password, user.password);
     return passwordCorrect ? user : null;
   }

   login(user: User): LoginResult {
     const payload: JwtPayload = { sub: user.id, login: user.login, role: user.role };
     return {
       accessToken: this.jwtService.sign(payload),
       login: user.login,
       name: user.name,
       role: user.role,
     };
   }
 }

    • Linha 16: [const port = process.env.PORT ? parseInt(process.env.PORT, 10) : 8080;] — a porta padrão, 8080, é a mesma do servidor Spring Boot original.

    4.10. Verificação de ponta a ponta

    Esta etapa foi verificada com cerca de dez cenários com curl contra uma cópia de teste do servidor (banco de dados em memória, pré-populado com as duas contas admin/admin e user/user):

    • POST /login com as credenciais corretas retorna corretamente { "status": 0, "data": { "accessToken": "...", "login": "admin", "name": "Administrator", "role": "ADMIN" } };
    • POST /login com uma senha incorreta retorna 401 Unauthorized (formato JSON nativo do [NestJS], e não o envelope [ServerResponse]<T>);
    • GET /getAllDoctors sem o cabeçalho Authorization retorna uma resposta 401 Unauthorized;
    • GET /getAllDoctors com um token JWT válido (admin ou user) retorna normalmente a lista de médicos no envelope habitual [ServerResponse]<T>;
    • POST /addAppointment com o token admin reserva normalmente um horário disponível;
    • POST /addAppointment com o token user retorna um erro 403 Forbidden, com a mensagem de que o papel [USER] não permite esta ação (papel exigido: ADMIN);
    • POST /deleteAppointment comporta-se de forma simétrica a /addAppointment, de acordo com o papel do token apresentado.
